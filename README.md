# 行程平衡器 · Trip Balancer 🧭

> 携程高校 AI HACKATHON 参赛作品 —— 多人旅行偏好平衡排程。
> 让每一次妥协都被看见:把每个人的「必去 / 想去 / 可接受 / 不去」整理成分层偏好,
> 结合**时间(每天 09:00–21:00 的时空窗)、预算、距离、天气**,生成一个大家都接受、
> 不吃亏的平衡行程 —— 并对**每个保留/取消项给出取舍解释**,把**谁在哪轮让步**记进公平账本。

## 意向与核心差异

多人旅行最常见的痛点:**意见不一致 → 一个人拍板 → 其他人一路妥协 → 体验打折**。
本作品不追求"谁都能接受但谁都不满意的平均主义",而是把评审的三条原则写进 AI 决策宪法:

| 原则 | 落地方式 |
|---|---|
| **平衡 ≠ 平均** | 偏好分四层,权重 `必去10 > 想去4 > 可接受1 > 不去(硬排除)`;作为决策宪法第 1 条强制 AI 遵守 |
| **防平均主义 / 必去优先** | 宪法第 2 条要求「每位成员的全部必去必须纳入」;**守门校验层硬性拦截**任何丢掉必去的方案 |
| **最低满意度 + 轮换优先权** | 让步账本只记「本可安排却未被采纳」的真让步,并在重排时把**欠账**(应得名额 − 实际拿到)作为**轮换优先权**注入 AI 上下文;补偿到位即归零 |

所有取舍都生成**可解释的决策**:为什么保留 X、为什么排除 Y、谁因此让了步。

## 产品形态

### 五栏主界面(底部菜单:社区 / 图鉴 / 创建 / 管理 / 个人)

| 栏 | 做什么 |
|---|---|
| **创建** | 建行程:**可搜索的城市选择器**(选项来自后端 `/api/cities`,新增城市数据即自动出现)、天数(1–7)、总预算、**初始人数(1–8)** 可调;人数实时联动文案,并在「偏好」页预置同等数量的待填写成员位 |
| **管理** | 行程列表(未开始 / 进行中 / 已完成徽章、预算进度条);每张卡可**📤 分享到社区**或删除 |
| **图鉴** | 打卡收集:行程「已开始」后按天**自动打卡**,也可手动点亮/取消;支持**按类型 / 人均价格 / 开放时段分组**;城市**逐个展开收起**、可隐藏未打卡城市与地点(偏好本地持久化) |
| **社区** | 行程分享帖信息流 —— 帖子**只能**由管理页的「📤 分享」产生;可挂景点卡、按**地点或按天**分段附**照片 + 文字点评**;支持点赞(可撤回)与评论 |
| **个人** | 昵称/头像/签名与收集统计 |

### 行程工作区(四页:偏好 → 规则 → 行程 → 公平)

1. **建行程** —— 城市、天数、总预算、初始人数
2. **「偏好」页**(每人一栏,两件事都在这页)
   - **景点意愿**:自然语言一句话,AI 解析成四层 POI 偏好;或榜单式点选拖动
   - **偏好意愿**:模糊软偏好(出行方式/体力/天气/消费倾向/作息/行程密度/单点紧迫度/住宿/社交/饮食),从**固定词表**中选,同样用「分类搜索 + 四段榜单」
   > AI 理解过程**分两步可视化**:① 解析景点意愿 → ② 解读偏好态度,逐步显示结果。
   > 填完点底部 **「设置全局规则 →」** 进入下一页(至少要有 1 位成员)。
3. **「规则」页**(全队排程规则)
   - 活动关联优先级 / 冲突解决 / 日程对齐 / 时间密度,分类型控件,支持一句话 AI 预处理
   - **已有一套默认值,不自定义也可以直接生成行程**
   - 底部主按钮 —— 未生成过是「**生成行程 🧭**」;**行程已开始后变「更新行程 🔄」**
4. **「行程」页** —— 逐日时间轴(含出行方式/时长/花费、逐日真实天气),每项可展开「为什么保留/取消」
5. **「公平」页** —— 回答「**谁被牺牲了、被牺牲了多少**」,而不是满意度百分比:
   - 每人一张卡:必去覆盖 `2/2 ✅`、意愿命中 `3/9`、**拿到 3 / 应得 2.0**
   - 颜色看**整数缺口** `deficit`(0 足额 / 1 欠 1 个 / ≥2 欠更多)—— 2 天行程只有几个名额,
     比率差一个名额就摆动 33–50%,做阈值纯是噪声
   - **没提意愿的人显示「未提意愿」,不是 0%** —— 没提要求 ≠ 极度不满
   - 软偏好由 AI 在行程定稿后**自评**一次:`✓ 被照顾` / `✗ 没体现` / `⚠️ 被违反`
     (软 `refuse` 不被守门层拦截,这里是唯一能揭出「声明不吃辣却排了麻辣火锅」的地方)。
     **裁决权归 AI**,确定性代码只防伪(不信编造的 tag id / 词表外的标签 / 该成员没声明过的标签),
     不预设"violated 只针对哪一层"这类层级规则;模型漏答某条已声明标签时**补问一次**并重新归一化,
     仍漏答则显示「? 未获评估」—— 绝不静默丢弃,也绝不落成 0%
   - 让步时间线只记**真让步**(本可安排却未被采纳),排不下/被他人明确拒绝只作解释材料

> **行程已开始后**的改动都在「偏好」「规则」两页完成:改完诉求点「更新行程 🔄」,
> 已冻结的天原样保留、只重排剩余天,让步账本**不重复记账**。
> 「偏好」与「规则」两页的信息都持久化在服务端(`Participant.pref`/`Participant.soft`/`TripState.settings`),
> 来回切换不会丢失。

### 决策引擎:纯 AI 编排 + 确定性守门

**白盒排程引擎已彻底移除** —— 行程完全由 AI 决策:

```
上下文(景点意愿 + 扩展软偏好 + 全局推荐设置 + 决策宪法 + 逐日天气)
   → AI 生成逐日草案(JSON)
   → 守门校验:时间窗 / 预算 / refuse / 开放时间 + 每位成员『必去』覆盖率
   → 不通过 → 失败清单回喂 AI 修正(≤2 轮)
   → 仍不通过 → 抛错(HTTP 422),**不做任何确定性兜底**
   → 通过 → 组装 PlanResult(公平账本、逐项解释)
   → 定稿后 AI 再自评一次软偏好达成度(失败则降级为「未评估」,不阻断)
```

- **为什么敢去掉白盒**:新引入的偏好(天气/体力/生物钟/消费倾向/密度)本质是模糊软偏好,
  硬编码进目标函数既重又不准 —— 正是 LLM 的强项。
- **守门层守什么**:只守硬地板,并区分**严重程度** ——
  **阻塞**(某人『必去』缺失 / 方案为空)→ 回喂 AI 重排,仍不达标则 422;
  **可裁**(非必去项当天放不下 / 被他人拒绝)→ 直接剔除并继续,由让步账本如实记录。
  这正是人类规划师会做的取舍,不必为此整体失败。
- ⚠️ **运行前提**:需要网络 + 有效的模型 key(见下方「AI 决策端」)。`LLM_PROVIDER=mock` 只提供**偏好解析**,
  不再具备排程能力(调用会显式报错,不静默降级)。

### 数据与口径要点

- **POI**:每城约 25 个精选地点(含门票/开放时间/建议时长/标签),数据文件即「可拓展的城市」,
  新增城市自动出现在创建页选择器里。
- **软偏好词表**:`preference_vocab.json` 是前端榜单池、AI 提示、自评归一三方的**单一来源**。
- **帖子照片**:前端 canvas 等比压缩(最长边 1000px / JPEG 0.7)后以 **base64 data URL 内嵌在帖子里** ——
  内存态演示不做文件上传、不落盘;限流每段 ≤4 张、每帖 ≤9 张。帖子是**内容沉淀**:
  段落标题冗余存储,来源行程被删后仍能完整渲染。
- **自动打卡**:`store.sweep_checkins()` 幂等推进 —— 只补「已过完整天」的 POI;
  打开行程或图鉴页时触发,行程走完后(含最后一天、单天行程)会补齐。

## 运行方式

```bash
# 后端 —— 端口用**默认 8000**(前端 vite 就代理到这里)
cd backend && pip install -r requirements.txt
python -m uvicorn app.main:app --reload        # 默认 8000;文档:http://127.0.0.1:8000/docs

# 前端(另一终端)
cd frontend && npm install && npm run dev      # http://localhost:5173
# vite 已把 /api 代理到 127.0.0.1:8000,浏览器打开 localhost:5173 即可
```

> ⚠️ 后端必须跟 vite 的代理端口一致(默认 8000)。端口不一致 = 前端代理打空,页面所有请求
> 一起失败(浏览器报 500),但**后端日志里什么都没有** —— 很容易误判成"AI 挂了"。
> 改端口的话 `frontend/vite.config.ts` 的 `proxy.target` 要同步改。
> ⚠️ `--reload` 在本机不可靠,改后端代码后**手动重启**。

**AI 决策端(必需)**:移除白盒后,行程生成完全依赖真模型。**任意 OpenAI 兼容端点均可**。

配置写进 `backend/.env`(已被 `.gitignore` 忽略,**不会入库**):
```bash
cp backend/.env.example backend/.env      # 然后填自己的 key
```
```ini
LLM_PROVIDER=deepseek        # 启用真实模型(也可写 llm / openai)
LLM_API_KEY=sk-xxx
LLM_BASE_URL=https://api.deepseek.com/v1   # 缺省即官方端点;换成任意兼容网关亦可
LLM_MODEL=deepseek-flash
LLM_ASSESS_TIMEOUT=60        # 软偏好自评超时,慢模型必须调大,见下
```
> 也可以照旧用环境变量传(`export ...`),**显式环境变量优先于 `.env`**,临时压测不用改文件。
> 兼容旧变量名 `DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL` / `DEEPSEEK_MODEL`(通用名优先)。

> ⚠️ **改完 `.env` 必须重启后端。** 环境变量是在**进程启动时**读进去的 —— 对已经在跑的服务
> 改文件没有任何效果。这正是"token 明明换过了却还是 401"最常见的原因,而且**症状会骗人**:
> 前端 vite 把 `/api` 代理到 **127.0.0.1:8000**,只要 8000 上还挂着旧进程(哪怕是 `provider: mock`
> 的空壳),浏览器看到的就是旧的失败。**排查第一步永远是 `curl 127.0.0.1:8000/api/health`**,
> 确认 `provider` 与 `ready` 再谈别的。

未配置时 `/api/health` 返回 `ready: false`,生成行程会返回 502 并给出可读提示。

> **实测延迟(同一份上海 3 天 / 2 人载荷,差距极大 —— 演示选型看这里)**
>
> | 模型 | 单次规划 | 说明 |
> |---|---|---|
> | 快模型网关 | **1.0s** | 快,适合现场演示 |
> | DeepSeek `deepseek-flash` | **39–87s** | 波动大,不宜现场演示 |
> | DeepSeek `deepseek-v4-pro` | 53–58s | 更慢 |
>
> - ⚠️ `deepseek-chat` 是**别名,静默指向 `deepseek-flash`**,想用 Pro 必须显式写 `deepseek-v4-pro`。
> - ⚠️ **`LLM_ASSESS_TIMEOUT` 默认 20s 是按快模型定的。** 软偏好自评在 DeepSeek 上要 ~39s,
>   超时后 `assess_soft` 会**静默降级为「未评估」** —— 不报错,只是公平页的软偏好整列变空。
>   换慢模型请设 `LLM_ASSESS_TIMEOUT=60`;快模型下请调回 20(别让一次卡住多等一分钟)。
> - ⚠️ **后端刚启动后的第一次调用较慢**(含 TLS 握手与网关预热)—— **演示前先跑一次预热**。
> - ⚠️ 不要用推理型模型:更慢,且会漏「必去」约束(守门层会拦下并 422)。

## 阶段性开发说明 & After Demo 规划

当前版本是**可完整跑通的单机 Demo**:行程生成、公平账本、图鉴、社区、个人资料全链路可用,
数据为内存态(重启清空)、POI 为内置精选集、照片内嵌存储 —— 目的是把**决策内核与产品闭环**讲清楚、验到底。

### 阶段性开发说明(Demo 现状与边界)

| 维度 | 当前 Demo | 说明 |
|---|---|---|
| 用户体系 | 单用户(单进程、无登录) | 「个人」栏是当前使用者资料;成员是行程内的**多份偏好**,不是多个账号 |
| 存储 | 内存态,重启即清空 | 无 DB、无文件系统;照片以 data URL 内嵌在帖子里 |
| 数据源 | 每城 ~25 个内置精选 POI | 新增城市 = 加一个数据文件,创建页选择器自动出现 |
| 出行 | 城市内行程;移动时间按步行/打车估算 | 未接真实路网,距离为直线近似 |
| 照片 | 前端压缩后内嵌 | 未接对象存储/CDN |

### After Demo(尚未实现,按优先级排列)

1. **真实路网接入** —— 用真实路径规划替换直线距离与步行/打车估算,让时间窗与「别走太远」的诉求落到真实街网。
2. **真实 POI 数据库 / 用户共建** —— 接入真实 POI 数据源,或加入用户意见收集,维护一套有软件特色的 POI 库
   (评分、实拍、避坑点),与图鉴/社区打通。
3. **单端模式 ↔ 多端模式** —— 创建时可选择:
   - **单端模式**(当前主逻辑):一台设备上替全队填写偏好;
   - **多端模式**:邀请其他用户加入行程,**每个人只能编辑自己那一栏偏好**,
     全局偏好(规则)可由队长同时调整;与主页的用户系统联动。
   > **Demo 级多用户演示方案(当前可演示)**:单端模式下的「每人一栏」本身就是多用户的**界面原型** ——
   > 同一后端实例可被多台设备/多标签页访问(`vite --host` 已开),约定各自只操作自己那一栏即可模拟协作;
   > 行程通过 `?trip=<id>` 分享给同伴,同看一份行程与公平账本。
   > **阶段性目标**:引入用户系统(登录/身份)→ 成员与账号绑定 → 栏位级权限(只能改自己)→ 共享行程的实时同步。
4. **预算系统升级** —— 与分组模式结合:支持**个人定制化预算**(每人的可接受花费区间)与
   **智能分配**(在总预算内按人/按偏好分配额度,并把超支风险在排程前暴露)。

> 这些方向都不改变现有决策内核:AI 编排 + 确定性守门、公平账本、可解释取舍 —— 只是把数据源、
> 用户体系与预算模型接到真实世界。
